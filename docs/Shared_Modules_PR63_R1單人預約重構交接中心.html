00｜專案使命與不可偏離的目標

Shared Modules 是三個 Flutter App 的共同產品核心，目的為快速交付 Tiandi（天帝教親和網）、Wuxiang（無相氣學）、EachCore（電商）之 Android 與 iOS MVP 並上架。不能把 PR #63 變成獨立大型預約系統，也不能以 ZIP 數量、Commit 數量或 CI 綠燈作為完成標準。

每項改動必須回答：它解決哪個共用核心錯誤？影響哪些 App？有何端到端證據？是否引入另一套資料契約？

01｜核心架構定義（使用者已核准）

Core 不得被任意拆分：認證、會員、權限、設定、通知、課程、活動、預約、簽到，皆屬共同核心，必須建立在一致的資料庫、Laravel 後端、Flutter 前端、業務規則、API 契約與測試之上。

其他次要功能按實際 MVP 需求評估；Tiandi、Wuxiang、EachCore 的專屬規則可透過設定與 App Adapter 隔離，但不得建立第二套核心預約資料模型。

技術基線：Flutter Android/iOS、Laravel + Filament、Sanctum、MySQL/MariaDB；EachCore 電商 MVP 的 WooCommerce 屬專屬整合，不強迫塞進共用核心。

02｜PR #63 唯一任務與禁止事項

PR #63 只處理 R1 單人預約重構與維持既有核心契約所需的必要依賴修正。目標：每位參加者一筆唯一正式預約；家庭代訂為授權關係，不再形成另一套 Group/Attendee 預約事實來源；統一狀態機、FIFO、取消、簽到與課程關聯。

  • 禁止繼續新增零碎功能、零碎 Commit、重複 API、永久雙軌資料模型、無截止條件的相容層。
  • 禁止自動合併 PR；禁止操作正式資料庫；禁止在整合驗收前啟用切換開關。
  • 不可因語法通過或 CI 綠燈就宣稱正式驗收通過。
  • 未完成依賴盤點前，禁止直接刪除仍被引用的檔案或資料表。

03｜已核准資料處理決策

決策 A：預約相關資料均為測試資料，可以重建，不需保留。目標是清除舊預約 Schema、舊 API、舊邏輯，建立唯一新架構。此授權不包含任何正式資料庫，也不代表可以不經確認刪除其他核心模組的表。

先列出資料表、外鍵、Migration、讀寫程式及測試依賴；再以乾淨測試資料庫驗證重建路徑。既有已執行 Migration 的環境與全新建庫須分別說明。

04｜已核准暫緩範圍

Outbox、Google Calendar、付款退款新增開發先擱置，待評估後再決定。不再以這些功能延伸 PR #63。已存在的付款／退款／通知／行事曆／簽到依賴必須盤點，確保 R1 清理不破壞原功能；需要改動時，先提出最小必要修正與風險，取得決策後才實作。

05｜現況基線與證據分級

GitHub 來源：PR #63；工作分支：refactor/r1-single-booking；原始規劃：refactor-r1-single-booking-plan.md。

先前 R1.74～R2.80 本機 ZIP 為未經完整 Laravel/MySQL/Flutter 驗證的暫存成果，不能直接當成 GitHub 已整合內容。每項結果須標記：已核准決策／GitHub 已存在／本機暫存／僅規劃／測試通過；不得混淆。

先前比對顯示 PR 分支與 main 存在差異；數量及 CI 狀態會變動，須於每次盤點重新查詢，不以本頁的歷史數值作為即時狀態。

06｜強制執行階段與出口條件

  1. A 凍結及逐檔盤點：GitHub HEAD × R1 × R2；輸出檔案矩陣（路徑、來源版本、現況、依賴、保留／改寫／刪除／待確認、證據）。未完成不得進入程式整合。
  2. B 唯一資料契約：定義 event_bookings 唯一事實來源、參加者／代訂者／權限、狀態、FIFO、取消、簽到／課程關聯及唯一 API。契約與驗收案例先核准。
  3. C 清除舊架構：追蹤 Flutter → API → Controller → Service → Model → DB；替換所有呼叫後刪除 Group/Attendee 舊路徑與過時 DTO、測試、Schema。不得留雙軌。
  4. D 測試：全新測試 DB Migration、MySQL 8.4、PHPUnit/Pest、Pint、Flutter 靜態檢查與測試、端到端本人／家庭／FIFO／取消／簽到／課程；必要時驗證既有付款關聯但不擴張功能。
  5. E 整合：全部程式完成後集中一次 Commit；檢查 PR diff、CI 與驗收證據，PR 不自動合併；經使用者核准後才合併。
  6. F 回到 App MVP：Tiandi 實際接入 Core，完成可操作 App、測試及上架準備，再讓 Wuxiang／EachCore 重用。

07｜交接中心強制更新制度

本 HTML 是 PR #63 的單一交接與決策入口。任何後續工作開始前，AI 必須先讀本頁與最新 PR；工作完成後，必須更新本頁的「最新進度、檔案矩陣、決策、風險、測試證據、下一步」。不允許只在聊天宣稱完成或只提供 ZIP。

若本頁與最新使用者指示衝突，以最新明確指示為準，並在決策紀錄說明覆蓋原因。修改本頁須和對應程式變更一起納入核准的整合 Commit；在未核准的階段不得藉更新文件偷偷推送局部程式。例外：本頁首次建立為使用者明確要求的 GitHub 文件提交。

08｜每次修改前自我稽核清單

  1. 是否直接服務三 App 的共用核心及上架？
  2. 是否遵守 Core 包含課程／活動／預約／簽到？
  3. 是否產生第二套 Schema、API 或狀態來源？
  4. 是否把暫緩的 Outbox／Google Calendar／付款退款當成新開發？
  5. 是否已追蹤前後端、Migration、測試的所有依賴？
  6. 是否把本機 ZIP 當成 GitHub 完成成果？
  7. 是否有真實測試證據，而非只有 php -l？
  8. 是否保持正式資料庫不動、PR 不自動合併？
  9. 本頁是否同步更新並留下可追溯的證據？

任何一項不符合：停止新增功能，回到盤點或決策階段。
