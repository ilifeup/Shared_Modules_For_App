# 課程管理 MVP｜一次性深入審查與整合實作基線

> 審查範圍：PR #53 分支 `mvp/single-member-booking-only`。本文為已讀程式的靜態審查，不代表測試通過、功能可上線。此文件優先於分散的課程 UI 待辦，避免重複新增 PR。維持 Draft、不得自動合併。

## 一、唯一產品目標

管理員在同一個「課程管理」入口，完成建立整期課程、安排每堂課、設定名額與價格、查看會員報名/候補、確認整期現金收款、請假補課及結案。重用既有活動 CalendarEvent、Booking/M11、現金帳單 Invoice，不建立第二套引擎。

### 管理畫面

1. **課程列表**：課程名稱、地點、第一堂與最後一堂、堂數、整期金額、正式名額、已占名額、候補人數、報名截止、可否報名；可搜尋/篩選。
2. **基本資料**：名稱、地點/樓層/教室、整期價格（整數，必填、預設 NT$1、最低 NT$1）、正式名額、候補名額（預設 5）、取消截止天數（預設 10）、付款保留時數（空白沿用全域）、報名截止。
3. **課堂安排**：按上課日期排序顯示每堂日期、開始/結束、地點、課堂狀態、補課名額（預設 1）；新增/修改課堂時重用活動欄位及驗證，不允許重複綁定同一活動。不得直接刪除已存在預約的課堂。
4. **報名與候補**：會員姓名、Email、代報者、報名狀態、候補順位、整期帳單號/應收/付款狀態、到期時間、收款時間；狀態篩選；所有狀態變更必須經既有 Service。
5. **財務**：整期一張帳單，管理員確認「實際收到現金」後才寫入付款流水；退款必須實際退還現金後再由管理員記錄；不得由表單直接改寫 paid/status。
6. **請假/補課**：原課堂請假原因、申請時間、截止時間、處理結果；補課連結目標課堂及唯一會員預約，保留歷史與 M11 出缺席一致性。
7. **例外**：付款逾期、無課堂、名額不足、候補無法遞補、報名後調整課堂、家庭代管失效、退款後仍占位，須有明確管理員處理入口及錯誤提示，不可靜默修復。

## 二、靜態審查發現（依風險排序）

### P0｜付款與課堂預約狀態不同步

- `CourseEnrollmentService::enroll()` 建立 `course_enrollments` 和整期帳單，**未建立每堂課 Booking**。
- `CashInvoiceService::confirmCash()` 直接把整期報名標記 confirmed 並記錄實收，**未建立每堂課 Booking**。
- 舊 `CourseEnrollmentService::confirmFee()` 才會建立每堂 Booking，但新 `paidCheck()` 遇到帳單會改走 `confirmCash()`，因此兩條路徑有重大語意落差。
- **驗收前必修**：決定唯一時點。建議依現行「付款保留名額」決策，在整期報名時原子建立 N 堂 Booking，付款確認僅記錄實收；逾期/取消必須釋放 N 堂 Booking 並遞補。整期只開一張帳單，單堂不開帳單。要先核對 BookingEngine 的唯一鍵、群組及鎖順序，不能只呼叫既有 book() N 次就宣稱安全。

### P0｜逾期釋放不完整

- `CashInvoiceService::expireDue()` 的整期路徑將報名改 cancelled、帳單改 overdue 並嘗試候補遞補；若前述 N 堂 Booking 已建立，必須同步取消所有 Booking，否則幽靈占位。
- `confirmCash()` 先鎖 invoice 再鎖 enrollment，逾期路徑也鎖 invoice、term、enrollment；與 `enroll()` 的 term-first 順序須統一，避免死鎖或併發搶位。

### P0｜舊免費/繞過帳單確認路徑

- `paidCheck()` 在找不到帳單時回退 `confirmFee()`；這可能將沒有真實 NT$1 現金收款與帳單的課程標記 confirmed。新規則：整期課程最低 NT$1，必須有有效帳單和實收才確認。既有舊資料要列出並人工處理，不能偷偷造帳。
- 早期契約 `docs/course-mvp-v2.4-contract.md` 的「沒有線上金流、交易或退款資料」及「付款後才建立 Booking」描述已與最新現金帳單/付款保留決策衝突；正式驗收以最新明確決策為準，並同步更新契約與測試。

### P1｜課程管理功能仍不完整

- 已有 Filament CourseTermResource CRUD、課堂/報名唯讀 RelationManager、帳單列表；但課堂新增/關聯、請假/補課管理、整期報名與候補統計、付款到期提示及狀態篩選仍不完整。
- 課堂編輯目前連到既有活動編輯，必須確認有報名者時的異動通知、名額、付款截止與已建立 Booking 的一致性。
- `course_terms.price_amount` migration 預設仍為 0，Filament 預設 1 與 Service 驗證 >=1，需規劃對既有 0 元資料的盤點；**不得自動把舊 0 元改成已收 1 元**。
- Filament 表單的 minValue/step 只是 UI，仍須在後端與資料庫層阻止無效輸入及非法修改已報名課程價格。

### P1｜測試基線與新規則衝突

- `CourseEnrollmentServiceTest::term()` 原本未設 price_amount，會拿到 migration 預設 0，與 enroll() >=1 驗證矛盾；本批已修正測試 fixture 為 1。
- 多個舊測試仍呼叫 `confirmFee()` 並假設付款後建立每堂 Booking，與新現金帳單流程不同；要整批重寫，不可只調整 assertion 使 CI 綠燈。
- 需要測試 12 堂全有 Booking、整期一張帳單、現金確認冪等、逾期原子釋位、候補 FIFO、管理員權限、同時報名/收款/逾期、重複 API 請求、會員請假補課與 M11。

**批次 B：完整課程管理**：單一 CourseTermResource 增加課堂安排、狀態篩選、正式/候補統計、報名及帳單連結、請假補課入口。所有寫入透過 Service，禁止直接編輯帳單、報名狀態或刪除有預約的課堂。

**批次 C：驗收**：在同一 HEAD SHA 跑 PHP/Laravel 測試、Filament CRUD、API、Flutter 與 M11 端到端；整理失敗案例及測試證據，人工核准前保持 Draft。

## 四、不可退讓的驗收條件

1. 20 人、12 堂、整期 NT$1：第 20 人成功，第 21 人進 FIFO 候補；每人 12 個有效課堂 Booking，僅一張 NT$1 帳單。
2. 12 堂任何一堂失敗：整期報名與所有 Booking、帳單全部回滾，不得部分占位。
3. 重試同一報名/付款不得重複建立 Booking、帳單、實收流水。
4. 未收現金不得顯示已付款；NT$1 必須真收；沒有帳單不能透過舊 confirmFee() 走捷徑。
5. 逾期或取消同步釋放整期所有課堂席位，候補嚴格 FIFO，整期一張帳單。
6. 補課占用獨立補課名額，在目標課堂一般名單與 M11 出勤中可見，不能額外建立目標期別整期報名。
7. 取消/請假期限前後端一致，已請假不能變缺課；無出席且未請假才缺課。
8. 僅單一管理員有管理權限；代管會員須重新驗證有效關係；不允許訪客與團體報名。
9. 已有報名的課程修改金額/名額/課堂安排時不得破壞既有帳單與預約。
10. CI 綠燈不等於正式驗收，必須附實機操作及資料庫一致性證據。

## 六、BookingEngine 整合前必須解決的帳單副作用（已查證）

- `BookingEngine::book()` 每次成功建立一般活動正式預約時，會呼叫 `CashInvoiceService::forEvent()`；不能直接對 12 堂重複呼叫 `book()`，否則可能產生 12 筆單堂活動帳單，違反「整期一張帳單」。
- 先在既有 BookingEngine 加入明確且只限內部課程流程的「由整期帳單涵蓋，不建立單堂帳單」選項；不可讓公開 API 任意傳入此選項來免付費。驗證 event、member、term、enrollment 的一致性後才可使用。
- 整期課程預約與唯一整期帳單須同一 DB transaction。使用固定 idempotency key `course-enrollment:{enrollmentId}:event:{eventId}`；每堂必須正式 confirmed，若任一堂不能取得名額，整批回滾，不能退化成單堂候補。
- 當期別逾期、取消或退款時，不可直接刪除 Booking；透過 BookingEngine 既有取消及稽核流程處理，並核對同步通知、候補遞補及資料庫鎖順序。若跨服務 nested transaction 的 side effect 未完全延後至 commit，須先補回歸測試。
- 目前 `confirmCash()` 已加上逐堂 Booking 存在檢查，會阻擋尚未整合的整期收款；此阻擋應維持至整期原子預約與逾期釋位完成，不能為了 CI 綠燈移除。

## 七、MVP 優先：簡化異常處理（使用者最新決策）

- 以能正常使用的課程管理 MVP 為第一目標，不為極少數「12 堂中有一堂預約失敗」建立額外補償引擎、重試排程、監控服務或複雜狀態機。
- 正常路徑：會員報名整期 → 以既有 Laravel DB transaction 建立各堂正式 Booking 與**唯一整期帳單** → 管理員確認實際現金收款。不能建立 12 張單堂帳單。
- 任一堂預約失敗時：使用既有 DB transaction 回滾本次報名/預約/帳單，回傳簡單清楚的錯誤訊息，交由管理員檢查；不開發自動修復機制。
- 仍須保留基本交易正確性、冪等及最少必要測試；「不過度設計」不等於允許部分扣款、幽靈名額或假付款。
- 先完成可操作 MVP：期別 CRUD、課堂安排、會員報名與候補、整期一張帳單、現金確認、基本名單。請假/補課與進階自動化只實作已核准的必要最小功能。
- 若既有文件出現「必須先開發完整例外狀態機／補償流程才可做 MVP」的解讀，以本節最新決策為準。
